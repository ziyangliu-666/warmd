# Design

## Background

On an A100 with driver 570 we measured about 160 ms to create a CUDA context, and the driver
creates them one at a time: about five per second per GPU, no matter how many processes ask. A
system that starts a new process per short task inherits that limit.

## Processes

```
client                         warmd
  app, cudart, cuBLAS ...        supervisor (no CUDA): socket, sessions, failover, metrics
  libcuda.so.1 from warmd  ----> active worker: the CUDA context, dispatch threads
                                 standby workers: context built, waiting
```

The client library (`src/shim.c`) implements the driver API by sending each call to the active
worker. Handles it returns are the worker's handles; device pointers are real device addresses.
Contexts are virtual: there is one real context, in the worker.

cudart 12 looks up driver functions with `cuGetProcAddress` by base name and version, so the
library maps names and, where signatures changed, versions. cuBLASLt `dlsym`s a fixed list of
symbols, so every symbol the real driver exports has a weak definition in `src/shim_stubs.c`,
generated by `contrib/tools/gen_stubs.sh`.

## Sessions

A client connects to the socket and sends its protocol version. The supervisor checks the uid
with `SO_PEERCRED`, picks a free region (or queues the client), and sends back two file
descriptors: a memfd holding the session's region and an eventfd. The client maps only its own
region.

A region starts with a 4 KiB header (state word, operation, arguments, results, error, a `dead`
flag), followed by a staging area and a ring for asynchronous copies. To make a call, the client
fills the header, sets the state to REQ and writes the eventfd. A worker thread runs the call,
sets the state to DONE and wakes the client with a futex. The client spins briefly before it
sleeps, and while sleeping it checks `dead` and the socket every 200 ms.

Worker threads share one epoll set with `EPOLLONESHOT`, so sessions run in parallel and each
session is handled by one thread at a time. Every session has its own stream, used as its
default stream, so sessions do not serialize on the legacy stream.

Asynchronous host-to-device copies are copied into the ring when called and DMA'd in stream
order. Device-to-host copies into pinned memory land in the ring and are copied out when the
client next synchronizes or a query reports completion.

When the socket closes, the worker frees the session's memory, streams, events, graphs and
link states, and the supervisor zeroes the region's resident pages before reuse.

GPU code is loaded once per worker. Images from mapped files are identified by file and offset,
others by a hash of their content.

## Failover

A sticky device fault (illegal address and similar) breaks the context for every session using
it, and it cannot be repaired: `cuDevicePrimaryCtxReset` keeps returning 700. So the worker
reports the session that saw the error and exits. The supervisor sets `dead` in every open
session (the fault code for the reporting session, 46 for the others), promotes a standby, and
starts a new standby.

The GPU needs 0.4 to 0.6 s to report a fault. In our tests new clients succeeded 20 to 150 ms
after that.

The supervisor cannot know which session caused an asynchronous fault: another session may see
it first. The Python pool finds out by rerunning affected tasks one at a time.

## Isolation

Separated between sessions: host-side memory (each client maps only its own memfd), ownership
of allocations and handles (foreign handles are rejected), device memory quotas, cleanup after a
client dies, the uid check at connect.

Not separated: device memory. Kernels in one context can read and write any address in it. One
daemon is one trust domain; give tenants that do not trust each other their own daemon on their
own GPU or MIG instance.

## Fork

A client holds no CUDA state, so a process can fork after CUDA initialization. The child drops
the inherited session and connects again on its first call. Handles it inherited from the parent
stay valid because they belong to the worker, unless a failover happened in between. The
welcome message carries the worker's generation number, and a child whose handles come from an
older generation fails immediately.

## Undocumented driver tables

cudart calls `cuGetExportTable` before any public API, and cuBLASLt uses a few more of these
tables. `src/shim_dark.c` implements the ones in use on driver 570:

| uuid prefix | used by | contents |
|---|---|---|
| `6bd5fb6c` | cudart | module loading from fatbins, primary context |
| `42d85a81` | cudart, cuBLASLt | tools TLS; slot 2 returns a tools object |
| `a094798c` | cudart | tools callback buffers |
| `c693336e` | cudart | context-local storage |
| `263e8860` | cudart | context checks |
| `d4082055` | every cudart copy | integrity hash, checked against the driver by `contrib/tools/ic_check.py` |
| `21318c60` | cuBLASLt heuristics | slot 4 sets its output to 1 |

The layouts of most tables and the hash come from ZLUDA. The `42d85a81` and `21318c60` behaviour
was found with `contrib/tools/etspy.c`, a proxy driver that logs table calls. These tables can
change with any driver branch.

## Adding a driver branch

1. `make`, then `contrib/tools/gen_stubs.sh` and commit `src/shim_stubs.c` if it changed.
2. `tests/run.sh` must pass and `contrib/tools/ic_check.py` must report MATCH.
3. If cudart or cuBLAS fail at start-up, run the program natively under the spy
   (`contrib/tools/etspy.sh`, then `ETSPY=all LD_LIBRARY_PATH=build/spy`) and implement the
   table entries it uses.
4. Add the branch to `VALIDATED[]` in `src/shim.c` and to compat.md.
